# AI-интеграция

В приложение встроен локальный LLM (по умолчанию **gpt-oss:20b** через Ollama /
любой OpenAI-совместимый сервер). AI используется для:

1. **AI-поиска** — естественно-языковое описание превращается в запрос к TheCocktailDB.
2. **Пост-обработки** — перевод инструкций на язык приложения.
3. **Доработки обычного поиска** — AI учитывает все выбранные фильтры (включая те, что
   TheCocktailDB не поддерживает напрямую) и решает, как построить один запрос.

## Локальный сервер

Ожидается **OpenAI-совместимый** endpoint `POST {AI_BASE_URL}chat/completions`
(Ollama, LM Studio, llama.cpp server и т.п.).

Конфигурация в `local.properties` (значения по умолчанию):

```properties
AI_BASE_URL=http://10.0.2.2:11434/v1/
AI_MODEL=gpt-oss:20b
AI_VISION_MODEL=qwen2.5vl:7b
AI_API_KEY=
```

- `10.0.2.2` — адрес хоста из Android-эмулятора. Для физического устройства укажите
  LAN-IP компьютера с сервером.
- `AI_MODEL` — текстовая модель (поиск, перевод); `AI_VISION_MODEL` — мультимодальная
  модель для сканера меню (`gpt-oss` не умеет изображения).
- `AI_API_KEY` необязателен; если задан, отправляется как `Authorization: Bearer …`.
- Для локального HTTP в манифесте включён `usesCleartextTraffic="true"` (только для
  dev-сценария; для production используйте HTTPS/локальную сеть по договорённости).
- Таймауты клиента: connect 10 c, read/call 180 c (20B-модель может отвечать медленно).

Пример запуска Ollama:

```bash
ollama serve
ollama pull gpt-oss:20b
ollama pull qwen2.5vl:7b
```

## AI-поиск

Экран «Поиск коктейлей» → раздел **AI-поиск**: пользователь описывает, что хочет
(например, «сладкий фруктовый коктейль»), и нажимает «Найти с AI».

Поток:

```
SearchDrinksScreen (описание + текущие фильтры)
  → AiSearchViewModel
  → AiSearchPlanner → AiClient → LLM
  → JSON с 1–3 запросами → SearchRequest
  → found_drinks → TheCocktailDB (несколько запросов, объединение)
```

Так как TheCocktailDB допускает **один фильтр за запрос**, AI возвращает **1–3
комплементарных запроса**. Репозиторий выполняет их по очереди и объединяет результаты,
удаляя дубликаты по `idDrink` (порядок: сначала результаты самого релевантного запроса).
Например «strong green with ice» → `[{"name":"Green"}, {"alcoholic":true}]`.

Промпт (адаптирован из [AGENTS.md](https://www.thecocktaildb.com/AGENTS.md) и
[SKILL.md](https://www.thecocktaildb.com/SKILL.md)) требует, чтобы **каждый запрос задавал
ровно один фильтр**; при необходимости нескольких ограничений возвращается несколько
запросов. Ориентиры:

1. явный запрос «безалкогольный/моктейль» → `alcoholic=false`;
2. упомянутые ингредиенты → `ingredient` (самый определяющий, обычно спирт);
3. бокал → `glass`;
4. вкус/настроение/повод → `name` (одно короткое английское слово) или `category`;
5. явный запрос «алкогольный» → `alcoholic=true`;
6. иначе — наиболее релевантный UI-фильтр.

Неподдерживаемые API параметры (`taste`, `color`, `skill`, `carbonated`) передаются в
промпт как подсказки. Прямая кнопка «ИСКАТЬ» по-прежнему использует одно
детерминированное условие без AI.

Ответ модели валидируется: если запросов нет или JSON не разобрался, используется
исходное условие. При недоступности сервера показывается ошибка (Toast), приложение
продолжает работать.

## AI-сканер меню

С экрана «Мои коктейли» (иконка камеры в тулбаре) открывается **AI-сканер**: пользователь
фотографирует меню/карточку коктейля (или выбирает фото из галереи), AI распознаёт название
и состав, приложение создаёт **локальный коктейль**.

Поток:

```
AI-сканер (фото) → AiScanViewModel → AiMenuScanner (vision) → JSON
   → если распознано уверенно (name + ингредиенты + confidence ≥ 0.5) → берём результат AI
   → иначе ищем коктейль в TheCocktailDB по названию (search.php?s=) → берём рецепт оттуда
   → показываем результат → «Сохранить» (фото меню идёт картинкой коктейля)
```

- результаты распознавания (название, ингредиенты, инструкция, бокал) показываются перед
  сохранением; количество/единицы парсятся `MeasureParser` (можно без граммовок — тогда
  `measure = null`); литеральные строки `"null"`/`"none"` от модели трактуются как пустые;
- если на фото есть **картинка коктейля**, vision-модель возвращает её bounding box
  (шкала 0–1000), и приложение **обрезает** эту область — она становится изображением
  коктейля; если картинки нет — используется фото целиком;
- фото сохраняется в app-private хранилище;
- при слабом распознавании или отсутствии ингредиентов подтягивается рецепт из базы
  (в UI помечается «Найдено в базе по названию»);
- если vision-модель не загружена/недоступна — показывается ошибка, остальное приложение
  работает как обычно.

## Пост-обработка рецепта

### Единицы измерения

TheCocktailDB отдаёт меру строкой (`"1 1/2 oz"`, `"4 oz frozen"`, `"1 cup fruit"`).
`MeasureParser` (`core/util`) разделяет её на **количество** и **единицу** из списка
`R.array.ingredient_unit`:

- поддержаны дроби (`1 1/2`, `1/2`, `½`), десятичные значения;
- синонимы (`tsp`→`teaspoon`, `ounce`→`oz`, `dashes`→`dash`, …);
- конверсии в допустимые единицы: `shot`→`oz` (×1.5), `cup`→`ml` (×240),
  `tbsp`→`ml` (×15), `pint`→`ml`, `quart`→`ml`;
- хвостовые слова игнорируются (`"4 oz frozen"` → `4` + `oz`, `"1 cup fruit"` → `240` + `ml`);
- если единица не распознана/недопустима — исходная мера сохраняется в количестве,
  единица остаётся пустой (данные не теряются).

Результат используется и при отображении деталей, и при сохранении в локальную БД
(`DrinkIngredientJoin.amount` / `unit`).

### Перевод

При открытии удалённого коктейля инструкция (`strInstructions`) при необходимости
переводится на язык приложения (`ru`/`en`) через AI:

- простая эвристика пропускает вызов, если текст уже на нужном языке
  (кириллица ↔ латиница);
- исходный рецепт показывается сразу, перевод подставляется, когда AI ответит;
- переведённый текст сохраняется вместе с напитком;
- названия ингредиентов, количества и единицы не переводятся (сохраняются как есть).

## Логи

В debug-сборке логируются и HTTP-запросы, и решения AI (Logcat):

| Тег | Что пишет |
|-----|-----------|
| `HomeBar-CocktailDB` | запросы/ответы TheCocktailDB и условия поиска (`Remote search conditions`, `returned N drinks`) |
| `HomeBar-AI` | HTTP к AI-серверу, промпт (`AI search request`), ответ модели (`AI search plan`), итоговые условия (`AI search conditions`) |

```bash
# всё сразу
adb logcat -s HomeBar-CocktailDB:V HomeBar-AI:V
```

Логи включаются только в debug (`BuildConfig.DEBUG`); заголовок `Authorization`
редактируется (`redactHeader`). В release-сборке логи выключены.

## Ограничения и безопасность

- AI — вспомогательный слой; источник рецептов остаётся TheCocktailDB. Модель не должна
  выдумывать рецепты, количества или ингредиенты.
- TheCocktailDB допускает только один фильтр за запрос — AI выбирает один, остальное
  игнорируется.
- Качество зависит от модели и промпта; план валидируется и при ошибке откатывается к
  прямым условиям.
- Локальный сервер должен быть доступен с устройства; при недоступности AI-поиск
  показывает ошибку, а обычный поиск и локальные данные работают как раньше.
- Ответственность за алкоголь: приложение не поощряет чрезмерное употребление; данные —
  рецептурный справочник, не медицинская/аллергенная сертификация.
